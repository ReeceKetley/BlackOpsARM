# Native SDK startup trace scan policy

2026-10-14. Two native-only source files are frozen for root's next SDK450/stage22 integration. This is removal of optional repeated diagnostic work after repeated actual rendered Com_Init proof; it does not skip or alter canonical initialization. Actual startup performance impact of this new pre-init policy remains pending the next real SDK observation. No new device run, headless benchmark, paired comparison or provider/asset/configuration change was made.

The preceding post-init scan removal already demonstrated substantial main/server CPU improvement in FACT0357. Root has real rendered Com_Init return evidence from SDK439 through SDK449. Those observations authorize disabling the optional pre-init address scan during normal rendered SDK launches; they do not replace the next run's startup timing evidence.

## Policy and exact placement

tools/port/engine/native_engine_trace.cpp now exposes the no-instrument C-linkage bool Bo1_ConfigureInitializationTrace(bool rendered). Its absent-override default disables the scan for rendered SDK entries and keeps the dedicated CLI scan enabled. BO1_TRACE_STARTUP strictly accepts only exact strings 0 and 1; empty, whitespace, extra digits, names and other values fail explicitly without changing the current flag. A valid 0 disables or 1 enables startup scanning for either owner, allowing verbose SDK boots to be restored. It logs actual enabled state, SDK/CLI owner and override presence to stderr; successful rendered SDK entry has already captured stderr in its private native-entry.log at that point.

The global initializationTraceEnabled atomic still starts true. Global constructor and early pre-entry instrumentation breadcrumbs therefore retain their historical behavior until the actual native entry validates SDK arguments/readable and writable roots, adopted Java/JNI context, chdir and output capture. RunNativeEngine calls the new configure function immediately after those checks and before spawning the watchdog, installing paths/policies and running actual Sys/PMem/Com_Init prerequisites. Invalid startup override returns a clear launch failure before watchdog creation. SDK rejection also reaches the existing SDL launch-error reporting path. Dedicated CLI default scan behavior remains enabled.

The existing Bo1_InitializationTraceReturned function and BO1_TRACE_POSTINIT validation/default/baseline switch are unchanged. That function remains called only after the actual Com_Init(commandLine) returns and its real initialization-completion owners are notified. BO1_TRACE_STARTUP=1 restores verbose startup but does not implicitly retain post-init scanning; BO1_TRACE_POSTINIT=1 remains the explicit existing post-init baseline setting.

## Preservation and expected avoided work

The instrumentation enter/exit hook bodies are unchanged. Disabled scans take their existing atomic flag check and return, avoiding the 14-target function-address scan on each instrumented function and the three separate write calls for matching functions such as Com_PrintMessage. Canonical Com_PrintMessage still runs and prints regular engine output; native fatal PC/stacks, native diagnostics, startup/service/error calls, asserts and UBSan/no-recovery remain. No function instrumentation, debug/O0 flag, validation, asset, SDL/DXVK/Vulkan provider or overlay/GPU source was changed.

Only native_engine_trace.cpp and src/platform/android/native_engine_runtime.cpp were edited. Root owns configuration, assets, device, source-build integration, STATE and Ledger; those were not touched. CMake source/link recipes need no changes: CLI and SDK each directly compile the same trace source, while both use the same native engine runtime archive.

## Verification

Evidence is build-android-audit/native_sdk_startup_trace_policy1. Actual CLI and SDK trace whole TUs compile, along with the shared runtime and unchanged actual SDL entry TU. Object symbols show a C-linkage Bo1_ConfigureInitializationTrace definition in each trace object and the matching undefined reference from the runtime object. Existing build.ninja closure inspection confirms each entry links its trace object plus the shared runtime archive; root's next shared build will establish the final linked artifact. No master/shared engine build was run independently.

Native before/after preprocessing confirms unchanged initialization-return baseline policy, instrumentation hooks, SDK capture, root/JNI validation and canonical RunNativeEngine body after removing only the newly added configure call/error branch. Source-order assertions verify capture before configure before watchdog, configure before Sys critical sections/PMem/Com_Init, and post-init policy after actual Com_Init return. Windows engine/oracle checks are not applicable to these native-only tools/platform files.

A bounded MSVC-host smoke harness extracts the exact production configure function and atomic behavior; only the environment pointer acquisition is injected to avoid Windows empty-environment differences. All 18 SDK/CLI absent/0/1/empty/00/whitespace/name/2/newline cases pass, including invalid values leaving the early trace flag unchanged. This is policy verification, not an engine simulation or performance benchmark. Two harness-only compile failures (flattened line comments and missing initializer_list include) were repaired in the harness; their logs remain retained. Actual production source/native compiles needed no repair. Final hashes/bytes, own diffs, native commands/preprocess/symbol logs and check-results.json are retained.

Next required evidence is the root-owned SDK450 integration: capture the logged pre-init enabled=0 owner=SDK override=0 policy and actual canonical startup progress/Com_Init return when reached, retaining fatal/regular output if a subsequent unrelated renderer blocker occurs. Report measured startup timing only after that run. No gain percentage or new startup duration is claimed here.

## Actual SDK450 integration

Root integrated both frozen files in SDK450/stage22. All seven packaged provider hashes match the stage manifest, install succeeded, and the new native-entry segment logs `pre-init startup trace scan enabled=0 owner=SDK override=0`. Actual canonical Com_Init returns and the real input/frame loop runs. Frontend reaches CA_ACTIVE at 78.161 seconds compared with SDK449 at 140.885 seconds. This is an observed launch trend, not a controlled paired benchmark or a steady gameplay FPS measurement. Regular output and real failures remain visible: the same run reports client FX bounds and independently captures a server GJK crash. Assets and protected providers were reused. See native_registry_closure/sdk-native-entry450-follow1-only.log and sdk-package-verification22.json.
