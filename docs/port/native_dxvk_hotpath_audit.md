# DXVK Native hot-path audit

2026-10-14, read-only audit of protected DXVK Native1.9.2. No provider edits, builds, config changes or device operations. Source candidates below are not measured performance gains. Root owns current SDK475 deployment and the actual comparison of the default-OFF filter-depth experiment.

## Actual device evidence

`build-android-audit/native_registry_closure/sdk-native-entry473-launch1-only.log:274–390` reports DXVK1.9.2, Adreno610, driver512.615.102, Vulkan1.1.128, graphics and transfer queue family0, 217 valid state-cache entries, and five compiler threads. Enabled features include host-query-reset and nullDescriptor, but not extendedDynamicState, transformFeedback or bufferDeviceAddress. No "Found config file" appears in that launch evidence; this does not establish the absence of every environment override or future config.

The accepted SUBOPTIMAL fix remains in `d3d9_swapchain.cpp:893–902`: SUCCESS/SUBOPTIMAL do not recreate the swapchain. `ANDROID-PORT-NOTES.md` records the prior clear247FPS/cube157FPS/three-pass56FPS spike after that fix, plus failed later rotation experiments. Those are historical toy-scene results, not current game performance. The protected binary is already described as release/O3 with asserts retained; merely recompiling DXVK release is not an identified missing optimization.

## Findings and actionable candidates

These require an explicitly separate ARM-owned experimental provider checkout/build, preserving the accepted provider and its binary hashes, Vulkan1.1 target, protected WSI and SUBOPTIMAL behavior. They are candidates for selective measurement, not authorization to modify the protected tree.

## Config options with limited or unsuitable expected benefit

`d3d9.deviceLocalConstantBuffers` defaults false (`d3d9_options.cpp:78`), but `CreateConstantBuffer:4800` already requests HOST_VISIBLE|HOST_COHERENT. Actual SDK473 memory types are type2=0xb, type3=0x7, type4=0xf. `dxvk_memory.cpp:tryAlloc` scans adequate types in order: if the buffer permits type3, default0x6 already selects a DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT type. Adding DEVICE_LOCAL likely selects that same type. Capture actual resource memoryTypeBits/selected type before spending a deployment on this toggle; no benefit is proved.

`dxvk.numCompilerThreads` defaults auto and currently selects five; state cache already reads217 entries. Compiler busy/pipeline growth counters can distinguish cold compilation from warmed rendering. Reducing compiler count may avoid transient CPU contention but cannot be represented as a steady GPU optimization without evidence. `dxvk.enableStateCache=false` would abandon an already functioning cache.

`d3d9.generalHazards` auto enables on this non-NVIDIA device (`d3d9_options.cpp:81–86`). `PrepareDraw:5913–5928` emits readback barriers for actual render-target sampling conflicts, and `MarkRenderHazards:5184` transitions implicated textures to GENERAL. `UpdateActiveHazardsRT:5145` already excludes different textures and nonzero target mip levels. Disabling hazards blindly is unsafe; record conflict frequency/identities and resolve actual aliasing before tuning. Source alone does not prove excessive barriers.

`samplerAnisotropy`, `strictPow`, `floatEmulation`, `longMad`, alpha-test wiggle room, MSAA and format-support options can change sampling/math/capability semantics or quality. They are not established quality-preserving fixes for this task. Current r_aaSamples1 is the accepted baseline. Present/max-frame-latency controls affect pacing/queueing, not total required shader/copy work; the room is well below30FPS and GPU-busy, so these are not supported primary remedies.

`Config::getUserConfig` (`util/config/config.cpp:677–709`) reads DXVK_CONFIG_FILE or relative dxvk.conf; it logs a successfully opened file. `dxvk_instance.cpp:16–18` merges application presets against the executable path, which current launch identifies as app_process64. A future config test must use an explicit application-accessible path and verify loaded option logging rather than assuming a Windows BlackOps executable-name preset applies.

## Measurement plan

Prioritize actual copy/render-pass count and total transferred bytes, then overwrite eligibility, framebuffer churn, constant and descriptor statistics. Existing `dxvk_stats.h` counters include draw calls, render-pass count, queue submissions/presents, pipeline counts/compiler busy and GPU idle ticks; they do not provide per-copy bytes or per-barrier timing. Existing game timestamp groups include queue/gap time and profiler perturbation. Add only bounded counters to a separate authorized experimental fork, pair with warmed same-scene timestamps and visual checks, then retain only proved gains.

The previous depth-unbind helper removes a legitimately unused attachment for guarded draws, but root's current comparison does not establish a material isolated improvement and the experiment is returning OFF. It should not be extrapolated into a blanket DXVK depth-attachment optimization. No source audit establishes that30FPS at unchanged resolution and quality is achievable yet; reducing unnecessary copies and setup is preferable to degrading the image, but the actual DOF/lighting shaders may remain the dominant cost.
