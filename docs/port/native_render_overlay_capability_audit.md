# Read-only rendered performance overlay capability audit

2026-10-14. User order is genuine rendering/gameplay first, then on-screen CPU/FPS/GPU/RAM metrics. This audit implements no overlay, changes no engine/provider source and runs no build, device command or benchmark. It identifies reusable owners and truthful labels so performance work can start after the renderer/gameplay gate is actually passed.

## Available measurements and limits

| Requested metric | Existing source / owner | Truthful initial display | Important boundary |
| --- | --- | --- | --- |
| FPS and frame time | DXVK HUD fps/frametimes; canonical RB_SwapBuffers; monotonic clocks | Render FPS, render interval ms | Count actual render/present activity, not the 20 Hz server tick, panel 60 Hz or Com_Frame calls. MAILBOX/compositor may discard submitted frames; submitted/rendered FPS is not exact panel-display delivery. |
| Frame CPU | Actual CLOCK_THREAD_CPUTIME_ID helpers in cpu_profile and engine_frame_timing | Main CPU ms/frame; render CPU ms/frame; separate Present wait ms | Thread CPU excludes sleep/descheduling. Wall frame duration includes them. Present-only CPU is not whole renderer CPU. Main/render scopes overlap and must not be summed blindly. |
| Process CPU | ProcessCpuNanoseconds →CLOCK_PROCESS_CPUTIME_ID | Process CPU % (100%=one core), or consumed core equivalents | All native/DXVK/Java engine-process threads; may exceed 100%. A share-of-all-cores percentage requires a separate clear denominator and valid system accounting. |
| App RAM | ReadProcessResources parses own VmRSS/RssAnon/VmHWM | App RSS MiB; optional peak RSS | RSS includes resident file/shared mappings. It is not private committed memory, PSS, system free RAM, native malloc heap or GPU usage. This APK's separate :engine process is the intended sampled process. |

PSS is slower accounting; native heap excludes mapped/hunk/GPU allocations. Do not substitute either silently for RSS. |
| GPU render time | Canonical rb_backend D3D9 timestamp/frequency/disjoint query ring, backed by pinned DXVK Vulkan timestamps | GPU ms when resolved; pending/unavailable otherwise | Real GPU work duration, not CPU Present time or hardware utilization%. No verified existing unprivileged Adreno hardware-utilization/thermal/frequency provider is present in these inspected owners. An unavailable hardware GPU percentage must stay unavailable; no assumed /sys permission, fabricated zero or CPU-wait proxy should fill it.

## Exact pinned DXVK HUD capability

Protected DXVK Native1.9.2 HUD supports version, devinfo, fps, frametimes, submissions, drawcalls, pipelines, memory, gpuload and compiler, plus D3D9 api and sampler items. This version has no built-in process CPU, process RSS/PSS or per-frame GPU-ms HUD item.

HudItemSet reads DXVK_HUD (or device config hud) when created. The fps item updates at 500 ms intervals. Its updates occur through the real D3D9 SubmitPresent command-stream path once per logical presented frame. It is therefore a useful real submission-rate indicator; it does not count server frames and cannot independently prove compositor delivery. The frametimes graph keeps a fixed 300-sample ring. GPU-load updates use the submission finish-worker's recorded empty-queue wait. Memory shows DXVK tracked per-heap used allocations and percentage of reported heap size; it does not display a real overall app RAM total.

A later development launch could request `DXVK_HUD=fps,frametimes,memory,gpuload,scale=2` before D3D device/swapchain creation without rebuilding/editing the provider. The protected working spike does exactly this through Android Os.setenv before library loading. In the current engine, this would be a launch-time diagnostic option, not an instant runtime toggle: the HUD selection is parsed at creation and there is no inspected public engine API to reconfigure it live. It cannot by itself satisfy the complete CPU/RAM/GPU-ms overlay request. Do not enable it now while proving first rendering.

The provider's GetAvailableTextureMem explicitly supplies a compatibility estimate, described in its source as inaccurate. Existing engine `availMB` based on that call must not become “RAM free” or a truthful physical GPU budget display. Optional VK_EXT_memory_budget handling exists internally, but without the extension it falls back to heap size/allocator accounting; those values need availability/source labels and no Vulkan upgrade is required or recommended.

## Real GPU timestamp feasibility

The protected working spike's retained final-cube.txt records **19,200,000 Hz timestamp frequency and 236 successful GPU samples**; final-cube-hud.txt also records 236 samples with HUD full enabled. Earlier provider identity evidence shows the same pinned SDL/DXVK bytes are used by this engine. That is real same-device/provider timestamp feasibility, not full-engine GPU-query or gameplay timing proof. Toy FPS/GPU durations should not be substituted for engine performance.

Existing rb_backend creates 8 query sets, each with actual TIMESTAMPDISJOINT/FREQ/begin/end plus optional phase marks. It issues timestamps around GPU frame work and polls GetData with flags 0; incomplete results stay pending, and failures/disjoint/no frequency are marked unavailable. DXVK's disjoint order is correct: Begin writes query1, End writes query0, so its end<begin test detects invalid ordering rather than marking every ordinary interval disjoint. Frequency is derived from the actual device timestampPeriod.

The existing resolved `gpuMs` excludes CPU-side Present waiting and measures GPU command time between the issued begin/end stamps. Keep its meaning and resolution latency visible; pending or stale samples must not show 0 ms. A small coarse start/end query path is enough for the first overlay. Detailed phase marks are optional diagnostics and should not be required for basic metrics. Query lifetime/device reset/surface loss and shutdown must remain owned by the actual render/device owner.

## Existing profiler hazards to avoid when wiring

The old bo1_frameperf path is valuable diagnosis, but enabling the entire logger for an everyday HUD also enables all profiling zones/first-use resource accounting, a process-thread enumeration refresh and per-task proc CPU reads around each Present. Its run-level vector grows over time and is copied/sorted for reports. That is unnecessary overhead for a lightweight on-screen panel. Reuse narrow clocks and actual boundaries without automatically switching on the whole logger.

RB_BO1PresentEnd currently increments its ring frame even when RB_SwapBuffers skips Present for high-resolution screenshots or resize. A successful D3D Present can also return without a live swapchain in the provider's surface-loss path. Consequently neither a blind ring counter nor hr==0 alone establishes a visible frame. FPS wiring must gate on the actual active surface/real Present path, handle background/surface loss, and present a submission/render rate label rather than fabricate screen-delivery proof.

BO1RenderFrame is an existing fixed32/volatile ring with delayed GPU writes. A new Java/UI reader should not directly copy raw entries across threads and assume volatile supplies publication safety. Aggregate on the owning main/render thread, then publish a separate bounded snapshot with real synchronization. Read only valid resolved samples and guard overwrite/age. Keep all existing packed/runtime ABI assertions unchanged.

The current main timing helper only enables while com_sv_running is true and reports by server wake groups. It is not ready-made FPS/main-CPU data for front-end menus. A rendered overlay must deliberately cover real menu/client frames too and must not map the headless server counter to FPS.

The RSS provider combines memory and FD-count sampling as one success result. Own-proc status may be readable even if an unrelated FD enumeration fails. A narrow memory-only observation API can be factored later if needed; no existing failures should become 0 MiB. Every procfs/clock/JNI failure must retain an explicit unavailable flag and sample age.

## Proposed minimal wiring after genuine rendering/gameplay

1. Add a narrow Android overlay observation owner. Keep bounded fixed-size accumulators on real main/render owners; record CLOCK_MONOTONIC intervals and actual thread CPU at frame boundaries. Count only the actual rendering/presentation path. Sample whole-process CPU on a 500 ms window and process RSS about once per second. Optional PSS can run at a slower cadence on a non-render/UI worker. Never scan all threads or query every asset per frame.
2. Reuse the genuine renderer timestamp owners behind a separate lightweight overlay-enable control. Poll completed GPU queries without flushing, waiting or adding a new Vulkan dependency. Publish GPU sample validity, age and pending/unavailable states. Keep detailed shader/resource/phase profiling off unless explicitly requested.
3. Publish a compact snapshot using a short mutex or appropriately synchronized atomic fields. The UI JNI getter copies this cached snapshot only; it performs no render-owner dispatch, proc scan or GPU query. Avoid raw volatile/seqlock payload races and per-frame synchronous JNI/UI calls. Measurement helpers should stay outside the function tracer where appropriate, as existing frame timing helpers already do.
4. Add a small non-focusable, touch-transparent TextView to the real EngineActivity's existing SDL layout on the Android UI looper, or a NativeUi lifecycle owner. Matching SDLActivity already has an actual ViewGroup containing its SDLSurface. Poll cached native data on a 500 ms Handler cadence, pause on activity pause/surface loss, remove callbacks/view on destruction. Preserve controller/touch focus, render-owner thread and real once-initialized process/lifetime behavior.
5. Provide a user-visible performance-overlay toggle after rendering works (for example a launch setting plus a queued engine console toggle). Read/save preference on its proper owner; publish an enable flag rather than letting Java mutate renderer objects. Initially show `Render FPS / frame ms`, `CPU process %`, `Main/render CPU ms`, `GPU ms or pending/n/a`, and `App RSS MiB`. Never print placeholder performance before real samples. A hidden overlay should stop UI refresh and optional expensive GPU/RAM diagnostics rather than continue background work.

Proposed implementation would primarily touch existing canonical frame/present boundaries, a small Android metrics owner, EngineActivity/NativeUi and matching JNI registration. Protected DXVK/spike sources and libraries do not need modification for these initial metrics. None of that wiring is implemented by this audit; parent first continues genuine renderer/gameplay integration as requested.

Evidence: `build-android-audit/native_render_overlay_audit1/readonly-source-manifest.json` records 19 inspected source/evidence hashes, including protected provider/spike files. sdk35-memory-api-signatures.txt records actual SDK public methods. Reports/artifacts were written with explicit UTF-8 and staged/read back. No engine source, asset, provider, compiler flag or device state was changed; no build/test/benchmark or hardware measurement was performed.
