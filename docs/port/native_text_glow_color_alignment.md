# Native text glow color alignment

2026-10-14. One bounded Android native ABI repair in canonical `src/gfx_d3d/rb_backend.cpp`; root owns SDK integration and Ledger. SDK438 uses the prechange source and its evidence remains valid. No runtime GlowColor failure has been observed.

The read-only first-2D-render audit follows SCR_UpdateScreen/SCR_UpdateFrame through CL_DrawScreen and R_EndFrame to RB_RenderCommandFrame, render-command dispatch, DrawText2D/quad drawing, code constants and tess vertex upload. The immediate float array paths are already scalar or byte copies: R_SetVertex2d/3d/4d write actual XYZW/texture lanes; R_SetCodeConstantFromVec4 and R_UpdateCodeConstantFromVec4 use four actual float components; R_CmdBufSet2D copies full declared matrices via memcpy; Vec2Copy/Vec3Copy/Vec4Copy use scalar components; R_SetVertexData uses Com_Memcpy, whose active body calls memcpy. No broad float/vector repair is warranted by this audit.

One structurally proven color alignment hazard is in GlowColor (original line3795). GfxColor is a union of uint32 packed and byte array[4], naturally aligned to four bytes. The old expression dereferences both source and destination as _WORD at (&packed +1 byte), necessarily an odd address even when the union itself is correctly aligned. The two-byte span stays within the real object and represents color bytes1 and2; this is an alignment/type-access problem, not a format-size defect.

The actual caller DrawText2D uses its own stack GfxColor finalColor as output and passes forcedGlowColor by value. In the second glow pass, with renderFlags&0x20, GlowColor copies forced RGB while retaining output alpha. SetDrawText2DGlowParms sets renderFlags|=0x30 when a nonzero-alpha glow color is supplied, providing a concrete canonical producer contract. Plain RB_DrawText passes renderFlags0 and does not activate this forced-color branch. The finding can matter to frontend text with explicit glow; it is not evidence that plain loading text or the next launch necessarily reaches it.

Android with BO1_NATIVE_64BIT now assigns result->array[1] and result->array[2] from forcedGlowColor.array[1]/[2]. The existing byte0 assignment follows unchanged. This preserves the exact original two copied byte values, RGB ordering, alpha, by-value source lifetime, glow formulas, return behavior and draw sequencing. Original Windows expression remains verbatim in #else. No declarations, object alignment, packing, assets, shader bytecode, UBSan/assertions, callbacks, Vulkan providers or metrics changed.

Nearby cast distinctions: RB_LookupColor destinations are actual GfxColor locals and R_SetVertex3d/4d_0/WithNormal callers use GfxColor or the four-byte color at offset12 of float3+byte4 GfxPointVertex, so these observed owners already supply four-byte alignment. The color_table source read at RB_LookupColor3646 has only a byte-array declared alignment contract; this is a nominal contract concern, not a structurally odd address or observed runtime violation, and remains unchanged. GfxCodeImageRenderTarget's _QWORD reads address an eight-byte bitfield-backed native union, rather than a float/color array; they do not belong to this proven family.
