# Production image uploads and SM3 math integration, stage44

Native image QueueUpload now enqueues the latest immutable CPU snapshot per actual Texture2D. The uploader validates complete mip/layer coverage and payload sizes, batches subresources into at most64MiB staging allocations (16-byte offsets), records real buffer-to-image copies and per-subresource layout barriers, submits offscreen work and waits the actual frame fence. Large images may span batches; individual subresources over64MiB currently fail explicitly. Initial copies use UNDEFINED, subsequent copies use submitted shader-read layout. Readiness is tied to the completed immutable snapshot, not copied CPU bytes.

Staging remains owned until GPU completion. Recording/submission/wait failures retain staging and restore pending snapshots; the uploader refuses further flush/readiness after a submission failure until device retirement. Clear waits idle when failed staging remains before releasing it. These failure paths compile but have not been fault-injected on the tablet. Queue snapshots and defined-layout state are protected against CPU loader access by a mutex; GPU work remains on the presenter owner. CPU decoded snapshots are still retained, so memory/streaming policy needs further measurement.

The canonical resource queue has a source-scoped native PreLoad branch validating the real native image owner. Actual uploads flush before ResourcesFlushed is published, and before EngineFrames starts recording. This replaces the null COM PreLoad without fabricating residency. Canonical per-image DB flush waits can still yield one-image groups; subresources within a group are batched. This is an integration implementation, not a measured mobile performance gain. General descriptor binding readiness and manual diagnostic upload paths are not universally unified with this uploader yet; full production frame execution remains unverified.
